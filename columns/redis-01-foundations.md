# Redis ①: 왜 메모리에 두는가 → 자료구조는 왜 여러 개인가

인기 상품 상세 페이지가 있습니다.

초당 5만 명이 **같은 상품**을 동시에 조회합니다.

매 요청마다 DB로 똑같은 `SELECT * FROM product WHERE id=501`이 날아갑니다.

DB의 CPU가 100%를 칩니다. 그런데 그 데이터는 1초 전과 한 글자도 다르지 않습니다.

> 방금 디스크에서 읽어온 값을, 다음 5만 명에게는 더 빨리 줄 수 없을까?

---

## 01. 왜 하필 "메모리"인가

디스크는 느립니다.

SSD라 해도 데이터를 찾아 읽는 데 수십~수백 마이크로초가 걸립니다.

메모리(RAM)는 그보다 **약 100배 빠릅니다.** 나노초 단위입니다.

이유는 물리적입니다. 디스크는 저장 매체까지 다녀와야 하고, 메모리는 CPU 바로 옆에서 전기 신호로 즉시 읽힙니다.

그래서 "자주 읽는 값을 아예 메모리에 올려두자"는 발상이 나옵니다. 이게 **In-Memory 저장소**, Redis입니다.

**그런데 메모리는 완벽하지 않습니다.**

비싸고, 용량이 작고, 전원이 꺼지면 사라집니다.

그래서 Redis는 데이터의 "원본"이 아니라 **빠른 복사본**으로 씁니다. 진짜 원본은 여전히 느린 DB에 있습니다.

---

## 02. 그냥 key-value 하나면 충분하지 않나?

아닙니다.

상품 조회수를 세는 상황을 봅시다. String 값 하나에 숫자를 담고 올린다면:

```
GET  count   → 100
+1           → 101
SET  count 101
```

두 요청이 동시에 `GET`으로 똑같이 100을 읽으면, 둘 다 101을 쓰고 **1이 유실됩니다.** (race condition)

그래서 Redis는 `INCR count` 라는 **한 개의 명령**을 줍니다. 읽고-더하고-쓰기가 쪼개지지 않고 통째로 실행됩니다(atomic).

**왜 원자성이 보장될까요?**

Redis는 명령들을 한 줄로 세워 **하나씩** 처리합니다(single thread). 내 `INCR`이 실행되는 동안 다른 명령이 끼어들 수 없습니다.

여기서 중요한 전환이 일어납니다. Redis의 "타입"은 단순 저장 형식이 아니라, **그 타입에 맞는 원자적 연산의 묶음**이라는 것.

그래서 무슨 타입을 고르느냐가 곧 무슨 문제를 풀 수 있느냐가 됩니다.

---

## 03. 타입마다 푸는 문제가 다르다

**Hash — 객체를 필드별로.**

사용자 정보를 String에 JSON으로 통째로 넣으면, 이름 하나 바꾸려고 전체를 읽고-고치고-다시 써야 합니다.

Hash면 `HSET user:1 name 민수` 로 필드 하나만 건드립니다.

```
user:1 ─┬─ name: 민수
        ├─ age : 5
        └─ city: 서울
```

**List — 순서 있는 줄.**

`LPUSH`로 넣고 `BRPOP`으로 꺼내면 작업 큐가 됩니다. `BRPOP`은 값이 생길 때까지 기다립니다(blocking).

**Set — 중복 없는 집합.**

"이 글에 좋아요 누른 사람"을 넣으면 같은 사람이 두 번 눌러도 하나로 셉니다. 교집합·합집합 연산도 됩니다.

**Sorted Set — 점수순 정렬.**

실시간 랭킹을 List로 만들면, 순위를 뽑을 때마다 전체를 정렬해야 합니다 — O(N log N).

ZSet은 **넣는 순간 이미 정렬된 자리**에 들어갑니다. 삽입 O(log N), 상위 10명 조회 O(log N).

그래서 리더보드·우선순위 큐는 ZSet이 정답입니다.

---

## 04. 규모가 커지면 타입도 트레이드오프가 된다

순 방문자 수(UV)를 1억 명 규모로 센다고 합시다.

Set에 방문자 ID를 전부 넣으면 정확하지만, 메모리가 수 GB로 폭발합니다.

**HyperLogLog**는 약 0.81% 오차를 감수하는 대신, 방문자가 몇 명이든 **12KB 고정**으로 셉니다.

정확도를 메모리와 맞바꾼 것입니다.

> 그러니 "무엇이 더 좋은가"가 아니라, **"이 카운트에 완벽한 정확도가 필요한가?"** 를 물어야 합니다.

---

이렇게 Redis는 "빠른 메모리 저장소 + 문제별 자료구조"가 됐습니다.

그럼 이 빠른 저장소를 실제 서비스에서 **가장 많이 쓰는 곳**은 어디일까요?
