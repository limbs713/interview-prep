# Redis ②: 캐시는 어떻게 동작하고, 왜 "갱신"이 아니라 "삭제"인가

①의 그 인기 상품 페이지로 돌아갑니다.

초당 5만 조회. 이제 우리는 Redis라는 빠른 저장소를 손에 넣었습니다.

그래서 붙입니다. "DB에 가기 전에, Redis에 먼저 물어보자."

이게 서비스에서 Redis를 쓰는 **가장 흔한 이유**, 캐시(Cache)입니다.

> 그런데 캐시를 붙이는 순간, 데이터가 두 곳에 존재하게 됩니다. 이게 모든 문제의 씨앗입니다.

---

## 01. Cache-Aside — 가장 기본적인 읽기 흐름

애플리케이션이 캐시를 **옆에 두고(aside)** 직접 관리하는 방식입니다.

```
읽기 요청
↓
Redis에 있나?
├─ 있음(HIT)  → 바로 반환 ⚡
└─ 없음(MISS) → DB 조회 → Redis에 저장 → 반환
```

처음 한 명만 DB까지 가고(miss), 그 뒤 5만 명은 Redis에서 바로 받습니다(hit).

**쉽게 말하면, "없으면 그때 채운다(lazy loading)"** 입니다.

---

## 02. 그런데 데이터가 바뀌면?

관리자가 상품 가격을 10,000원 → 8,000원으로 수정했습니다.

DB는 8,000원으로 바뀌었습니다.

그런데 Redis에는 아직 10,000원이 남아 있습니다.

사용자는 계속 **틀린 값**을 봅니다. 이것을 **stale(오래된) 데이터**라고 합니다.

캐시를 붙인 대가입니다. 데이터가 DB와 캐시 두 곳에 있으니, 한쪽만 바뀌면 어긋납니다.

그럼 쓰기가 일어날 때 캐시도 손봐줘야 합니다. 두 가지 선택지가 있습니다.

> 캐시를 **새 값으로 갱신**할까, 아니면 **그냥 지워버릴까**?

---

## 03. 왜 "갱신"이 아니라 "삭제"인가

정답은 대부분 **삭제**입니다. 캐시를 새 값으로 덮어쓰지 않고 그냥 지웁니다(delete-on-write, 또는 cache invalidation).

**이유 1 — 동시성.**

두 명이 거의 동시에 가격을 수정한다고 합시다.

```
A: DB=8000 저장 → 캐시=8000 갱신
B: DB=9000 저장 → 캐시=9000 갱신
```

네트워크 순서가 꼬이면, DB엔 9000이 남았는데 캐시엔 A의 8000이 마지막에 써질 수 있습니다. 캐시가 DB와 영구히 어긋납니다.

**삭제**는 이 문제가 없습니다. 둘 다 "지우기"만 하면, 다음 읽기가 DB의 최신값(9000)을 다시 채웁니다.

**이유 2 — 낭비.**

수정한 값을 아무도 안 읽을 수도 있습니다. 갱신은 "읽힐지 모르는 값"을 미리 계산해 넣는 낭비입니다.

삭제해두면 **실제로 읽는 사람이 생겼을 때만** 다시 채워집니다. 게으르게, 필요한 만큼만.

그래서 규칙은: **DB를 먼저 쓰고, 그다음 캐시를 삭제한다.**

---

## 04. 삭제를 놓치면? — TTL이라는 안전망

삭제 코드가 빠지거나, 삭제 요청이 실패할 수도 있습니다. 그러면 stale 데이터가 영원히 남을까요?

그래서 캐시 키에는 거의 항상 **TTL(Time To Live)**, 만료 시간을 겁니다.

```
SET product:501 "..." EX 300   # 300초 뒤 자동 소멸
```

TTL은 두 가지를 동시에 해결합니다.

첫째, 삭제를 놓쳐도 **최대 300초 뒤엔 캐시가 사라지고**, 다음 읽기가 최신값을 다시 채웁니다. 정합성의 최후 방어선입니다.

둘째, 아무도 안 찾는 키가 **메모리에 영원히 쌓이는 걸 막습니다.** (메모리는 비싸다 — ①을 떠올리세요.)

**그렇다면 TTL은 길수록 좋은가, 짧을수록 좋은가?**

트레이드오프입니다. 짧으면 항상 신선하지만 miss가 잦아 DB 부하가 늘고, 길면 빠르지만 stale 위험이 커집니다. "이 데이터가 얼마나 자주 바뀌고, 얼마나 틀려도 되는가"로 정합니다.

---

## 05. 다른 전략도 있다 (짧게)

**Write-Through** — 쓰기를 캐시에 하면 캐시가 DB까지 대신 써줍니다. 항상 최신이지만 매 쓰기가 느려집니다.

**Write-Behind** — 캐시에 먼저 쓰고 DB엔 나중에 몰아서. 빠르지만 그 사이 장애 시 유실 위험.

대부분의 웹 서비스는 단순하고 안전한 **Cache-Aside + delete-on-write + TTL** 조합을 씁니다.
